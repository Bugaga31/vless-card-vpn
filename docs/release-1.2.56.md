# VLESS Card 1.2.56

## Изменения

- В настройках Tor можно сохранить порог HTTPS-задержки 100 мс или другое
  положительное целое значение. Убрано скрытое ограничение 250–15000 мс при
  сохранении и применении. По умолчанию остаётся 2500 мс.
- В подборе цепочек «Баланс» и «Скорость» учитывается уже измеренная скорость
  передачи YouTube: более медленная медиапередача ограничивает оценку маршрута,
  даже когда обычный HTTPS-файл загружается быстро. Дополнительных запросов нет.
- Та же оценка используется при переключении живого маршрута с защитой от
  постоянных переподключений. Service FAIL, UNKNOWN, общий deadline и отмена
  не ослаблены.
- Проверка скриншотов требует элементы главной страницы, а не просто непустой
  экран приветствия. Это исправляет известную неточность визуального отчёта 1.2.55.

## Что этот выпуск не обещает

- Порог 100 мс не делает Tor физически быстрее; слишком строгий фильтр может
  исключить все измеренные страны. Обычное создание цепочек при этом продолжается.
  Для Snowflake сохраняется двойной порог.
- Это не гарантия отсутствия буферизации, максимальной скорости во всех сетях
  или выбора самого быстрого сервера интернета.
- Причина медленной загрузки голосовых не установлена. Тест MTProto не является
  измерением загрузки голосового сообщения.
- Доменная блокировка рекламы сохранена, но встроенную рекламу YouTube гарантированно
  не удаляет. Общие видеосерверы для этой цели не блокируются.
- Новых обученных нейронных весов в выпуске нет. Диалоговые эксперименты и
  адаптерное обучение остаются отдельной исследовательской задачей.
- Физический телефон, мобильные операторы и реальные мосты Tor этим выпуском
  автоматически не проверены. Лабораторный PASS не доказывает работу у оператора.

### Повторная ревизия релизной проверки UI

Первый релизный run 40185968278 (SHA 67bbbceb…) прошёл quality и подписанную
сборку, но остановился на `home-ui` API 34; публикация была пропущена. Подробный
лог недоступен, поэтому точная причина выхода не объявляется установленной.
В скрипте устранён недиагностируемый ранний выход при временной ошибке чтения
hierarchy/снимка: добавлены ограниченные операции, удаление устаревших файлов,
диагностика последней операции и штатное нажатие единственной кнопки приветствия.
Непустой PNG и настоящие элементы главной страницы остаются обязательными.
Это не ослабление gate и не доказательство причины первоначального сбоя.

### Изоляция E2E-состояния

Run 40187893871 (SHA 1da13421…) не прошёл E2E: обязательные server-side
проверки не увидели нужные endpoints в single/multi, хотя HTTPS-пробы передали
данные. Это не объявляется исправленной ошибкой production или доказанным
инфраструктурным сбоем. Все проверки server-side трафика сохранены.
Тестовый загрузчик теперь останавливает старый процесс перед заменой state.json,
ожидает запуска Activity и прекращает сценарий при ошибке импорта. Во всех
fixture-каталогах выключено внешнее обновление подписок, как уже было в Auto-
сценариях. Это исключает известные возможности вмешательства фоновых задач;
точная причина предыдущего сбоя по доступным аннотациям не установлена.

### Диагностическая ревизия

Отдельная ветка rebuild-e2e-diagnostics-167, SHA 07dc5a08…, run 40191277886,
прошла E2E API 29/33 и матрицу масок без ослабления требований. Добавлены только
ограниченные счётчики состояния/запуска/исключений и fixture-трафика; raw URLs,
credentials, payload и полный logcat в аннотации не выводятся. Debug-действия
по-прежнему закрыты BuildConfig.DEBUG. Такой успешный запуск не устанавливает
причину прежних сбоев и не означает, что все реальные сетевые проблемы устранены.
При переносе в release-build-167 полный релизный CI обязателен для нового SHA.

### Разбор присланного архива логов

Два присланных ZIP побайтно одинаковы; один содержит обе E2E-задачи итогового
SHA 2b0f1c4e…. API 29 подтверждает загрузку восьми fixture-конфигураций и наличие
разрешения VPN, но не запуск туннеля. API 33 подтверждает HTTPS-передачу через
VPN и трафик всех трёх серверов, затем `optimize result=false`.

В коде устранена установленная несогласованность debug-fixtures: преобразование
точных r163-pool-[0-7].test раньше выполнялось только в native-конфигурации Xray,
но не в предварительном DNS/TCP-фильтре. Теперь один debug-only преобразователь
используется в обоих местах; в release это тождественная функция. Это не
доказательство единственной причины исходного сбоя.

Тест оптимизации теперь ждёт завершения предыдущего foreground-действия в
пределах 60 секунд, затем проверяет фактическое исключение мёртвого сервера и
наличие рабочего fixture-сервера, а не только Boolean «этот вызов изменил состав».
После оптимизации добавлена повторная передача четырёх HTTPS-запросов другим UID.
Проверки трафика всех трёх серверов, 8-outbound Auto и отсутствие прямого обхода
сохранены. Исключение, пустой выбор и оставшийся мёртвый сервер не проходят gate.

Финальная локальная ревизия по присланным логам: Debug JVM 632, Release JVM 631; ошибок и пропусков нет. Release lint — 0 ошибок, 53 предупреждения, 2 информационных замечания. assembleRelease успешен. Python: 12 E2E, 49 release-gate и 45 cloud-тестов. Физический телефон не проверен.
