# Проверка ByeDPI / ByeByeDPI / zapret для Android 13

## Проверенные исходные проекты

- ByeDPI: https://github.com/hufrea/byedpi — локальный SOCKS-прокси с реализацией split, disorder, fake/TTL и TLS-record splitting.
- ByeDPIAndroid: https://github.com/dovecoteescapee/ByeDPIAndroid — root-free Android VpnService + ByeDPI + hev-socks5-tunnel.
- ByeByeDPI: https://github.com/romanvht/ByeByeDPI — Android-приложение на базе ByeDPI, с proxy/VPN режимами, импортом/экспортом настроек и per-app split tunneling. Оно само по себе не шифрует весь трафик и не скрывает IP.
- zapret: https://github.com/bol-van/zapret — документация Android явно различает nfqws/transparent tpws (нужен root) и tpws --socks (возможен без повышенных прав на обычном порту).

## Что есть в нашем приложении

В текущем APK нет бинарников/JNI ByeDPI, tpws или nfqws и их жизненного цикла. Имена старых Kotlin-пресетов (например, «Zapret Ghost» / «Fake Packets») не означают, что эти движки встроены. Генератор sing-box передаёт булевый TLS `fragment`; это не эквивалент NFQUEUE, fake TTL/sequence-number manipulation или полноценному набору стратегий ByeDPI.

`stable_tls` оставляет параметры сервера и проверку сертификата, отключает экспериментальную фрагментацию и случайную ротацию SNI. Это профиль совместимости, не новый протокол обхода.

## Реалистичный порядок интеграции

1. Сначала подтвердить холодный запуск на realme/Android 13, отсутствие падений нативного ядра и нормальное отключение VPN.
2. Добавлять отдельный, выключенный по умолчанию **локальный TCP Anti-DPI режим**, не выдавая его за шифрованный VPN: собственный один VpnService, встроенный ByeDPI или tpws --socks, TUN-to-SOCKS транспорт, защищённые/исключённые исходящие сокеты, корректная DNS-политика, остановка и очистка JNI-процессов.
3. Для каждого поддерживаемого ABI закрепить upstream commit, собрать через NDK, проверить лицензии и добавить лицензионные уведомления. Не скачивать исполняемые бинарники во время запуска из случайных источников.
4. Реализовать небольшое число реально поддерживаемых профилей, проверять доступность назначенных сайтов через реальный выбранный тракт. TCP ping недостаточен, а результат на одном провайдере не подтверждает работу у другого.
5. UDP/QUIC и ограничения IP/белых списков проверять отдельно: TCP-сегментация не решает все виды блокировок.
6. Шифрованный VLESS/Reality и локальный Anti-DPI режим должны быть явно различимы. Два внешних VPN-приложения нельзя просто одновременно включить для одного Android-профиля. Для цепочки нужен отдельный проверенный proxy-режим и контроль маршрутов/исходящих сокетов; соответствующий тракт не реализован в текущем релизе.
7. nfqws не включать на обычном телефоне без root и не предлагать отключать требования безопасности Android ради его запуска.

## Что проверено и что нет

Upstream README и текущие исходники нашего приложения проверены. Работоспособность стратегий в сети пользователя, совместимость с конкретным ядром/прошивкой realme и отсутствие утечек в будущей proxy-цепочке не проверены. Интеграция этих нативных движков ещё не реализована; в stability preview они не включаются.

## Публикация stability preview

Подготовлен шаблон `ci/stability-preview.workflow.yml`: side-by-side APK, unit/lint, Android 13 instrumentation tests, отчёты/скриншоты и prerelease с APK/SHA256 только после успешных проверок. Это пока **не активный workflow**: запись в `.github/workflows/` отклонена текущей GitHub-интеграцией (403). Тестовый APK и SHA256 опубликованы отдельным prerelease: https://github.com/Bugaga31/vless-card-vpn/releases/tag/stability-preview-9813d73. Автоматический workflow по-прежнему не активирован; Android instrumentation tests не запускались. Основная ветка и стабильный latest-release не заменялись.
