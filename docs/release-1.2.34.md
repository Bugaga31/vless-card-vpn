# 1.2.34 · Auto: исправление поиска, а не ещё один таймаут

После повторного сообщения о нерабочем Auto в 1.2.33 сравнили исходники с тегами `v1.0.100` и `v1.1.0`. Старый `quickTest` сначала проверял TCP всего списка и затем до 30 доступных маршрутов; новый поиск слишком зависел от небольшой начальной выборки. Полный откат старой реализации не сделан: её быстрый успех не доказывал Telegram MTProto и передачу видео.

## Исправления

- После неуспеха начальных подсказок — ограниченная широкая проверка до 128 адресов/транспортов, затем до 24 доступных кандидатов через фактические конфигурации. Это не перебор всего каталога; общий бюджет подготовки остаётся ограниченным. Обычное TLS-рукопожатие не добавлено как фильтр для всех протоколов.
- Следующая попытка исследует другую часть каталога. У каждого сетевого контекста свой ограниченный RAM-курсор; настройки и накопленные веса не сбрасываются.
- Явно недоступные по TCP начальные адреса больше не возвращаются обратно в волну через fallback. Таймаут остаётся неизвестным, UDP-транспорты не отбрасываются по отсутствию TCP.
- Неудача первых двух сервисных кандидатов не заставляет перескакивать сразу к непроверенным ссылкам: следующая волна сначала использует ещё не испытанные HTTPS-кандидаты той же группы.
- Незавершённый замер скорости больше не оставляет победителем маршрут с красивым ping и неизвестной передачей. Исторические значения сохраняются, но не выдаются за подтверждённую скорость. Явный игровой профиль сохраняет отдельную политику задержки.
- Если итоговая проверка реальной цепочки не прошла, её старые положительные подтверждения отзываются. Следующее нажатие не может мгновенно использовать их снова. Это не обвинение каждого сервера в пуле: нет массового штрафа/карантина; более новые замеры, другая маска и другая сеть защищены.
- По уточнённому требованию подключение больше не зависит от извлечения ссылки на один ролик. Auto проверяет реальную передачу через независимые HTTPS-ресурсы Cloudflare / CacheFly / OVH: нужны два разных TLS-хоста, полные ответы по 64 КиБ, корректный HTTP-статус и не HTML/JSON, до трёх попыток с отдельным таймаутом до 1,5 с в общем бюджете. Range и ограниченное чтение ограничивают полезную нагрузку до 192 КиБ на проверку, даже если ресурс игнорирует Range. Накладные расходы TLS/заголовков в этот предел не входят.
- Telegram MTProto и настоящее видео YouTube остаются отдельными проверками. Полностью подтверждённый сервисный пул имеет приоритет. Если таких маршрутов нет, допускается маршрут с двумя свежими HTTPS-передачами и неизвестными сервисными результатами: UI явно показывает «не удалось проверить». HTTPS не записывает PASS для Telegram/YouTube. Подтверждённый сервисный FAIL по-прежнему исключается.
- Сбой контрольного ресурса не превращается в массовый карантин. HTTPS-доказательство отдельно привязано к сети, маске и времени; смена цепочки его отзывает. Формат состояния дополнен полями без сброса истории или обученных весов.
- Эмуляторный стенд расширен точными HTTPS-хостами только в debug-конфигурации, с временным сертификатом и проверкой TLS. Release не получает тестовый корневой сертификат.

- Проверка CI выявила проблему отмены: обработчик хранил только последний HTTP-запрос из параллельных проверок. Теперь отменяются все зарегистрированные запросы, в том числе поздно созданные. Тест закрытия сокетов принимает штатные FIN и TCP RST, но не таймаут; проверка не отключена.

- Полный Android E2E выявил дополнительную первопричину: HTTPS/медиа-проверки сами поднимали счётчик активного трафика, после чего политика фоновых улучшений запрещала обязательный первый замер скорости. Auto не мог выбрать даже рабочий маршрут. Теперь ограниченный обязательный замер при первом подключении отделён от необязательного исследования. При живом туннеле защита пользовательского трафика сохраняется; тепловые/энергетические ограничения не сняты. Тесты не отключены, отсутствие замера по-прежнему не выдаётся за измеренную скорость.

## Границы результата

Эти изменения устраняют конкретные кодовые регрессии, но не подтверждают скорость или доступность у оператора пользователя. Недоступный контрольный YouTube-плеер не блокирует подтверждённую независимую HTTPS-передачу; UNKNOWN сервиса не превращается в PASS и не гарантирует работу видео. Поддержка ручного режима, действующие настройки DNS/split tunneling/kill switch, сертификаты, подпись Beta и данные обучения сохранены.

Регрессии покрывают доступный маршрут за пределами прежней начальной группы, ротацию поиска по сетям, переход к следующей сервисной паре, повторное нажатие после финального отказа, гонку новых доказательств, неизвестную скорость и быстрый отказ на локальном SOCKS-стенде. Эмуляторный видеостенд не является проверкой публичных сервисов в РФ.
