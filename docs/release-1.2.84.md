# 1.2.84 Experimental — очередь без голодания и TCP dual-stack подсказки

## Практическое исправление Авто
Обнаружен порядок операций, при котором импортированный каталог мог застревать на верхнем окне: ограничение дорогого ранжирования до 256 кандидатов выполнялось ДО отсева маршрутов с недавним провалом Telegram/охлаждением. Группа отложенных лидеров могла постоянно занимать окно, скрывая свежих кандидатов глубже каталога.

Теперь перед ограничением окна выполняется дешёвый проход по каталогу: сначала учитываются serviceRank и охлаждение именно текущей сети/маски, потом строится ограниченное окно ранжирования и выбираются разнообразные кандидаты. Если весь каталог отложен, ограниченная восстановительная попытка сохраняется; провалы не превращаются в вечный blacklist. Неизвестные серверы, глубокие транспортные семьи, сетевые профили и облачные подсказки не должны вытесняться сотнями охлаждающихся лидеров.

34 новых теста включают каталог из 1001 элемента, первые 1000 из которых охлаждены или имеют недавний провал Telegram, и доказывают допуск свежего элемента за этим префиксом. Это не доказательство доступности какого-либо публичного сервера.

## Быстрые TCP-подсказки: несколько адресов вместо первого
Tester.fastFilter больше не ограничивается InetAddress.getByName и первым адресом домена. Используются ответы текущего вызова getAllByName, чередование IPv4/IPv6 с сохранением первого предпочтения резолвера и порядка внутри семейства. Не более четырёх адресов, двух одновременных соединений, интервал 250 мс и один общий бюджет. Победитель отменяет оставшиеся сокеты. Это упрощённая Happy-Eyeballs-inspired предпроверка, а не полная реализация RFC8305: нет независимого потока A/AAAA, RFC6724-сортировки и собственной NAT64-синтезации.

- DNS для одинакового имени разделяется только внутри одного вызова fastFilter; новый межсетевой кэш не добавлен.
- DNS вынесен из общего пула сетевых проб в отдельные четыре фоновых потока и ограниченную очередь из 32 задач. Даже если libc-резолвер игнорирует прерывание, новые волны не создают неограниченное число DNS-потоков. Таймаут, переполнение очереди и ошибка DNS дают «неизвестно», не «мёртвый сервер».
- Отмена удаляет ожидающую DNS-задачу и закрывает зарегистрированные сокеты. Поздний DNS-ответ не меняет завершённую пробу. Адреса не подменяются и не сохраняются между сетями.
- Проверены реальные loopback-сокеты: недоступный первый адрес и доступная альтернатива. Это не испытание реального dual-stack оператора или NAT64 на телефоне пользователя.

**Граница применения:** fastFilter — вспомогательная TCP-предпроверка для соответствующих диагностических/восстановительных путей. Быстрый первый Auto-handoff по-прежнему запускает настоящие HTTPS/Telegram-пробы без обязательного TCP-фильтра. Массовый Tester.tcp и все внутренние диалеры Xray этим патчем не переписаны. TCP handshake и ответ DNS не считаются доказательством работоспособности VPN.

## Что не ослаблялось
- Авто продолжает искать до результата/отмены с энергозащитными паузами из 1.2.83.
- HTTPS и MTProto должны подтвердить 1–500 мс; неизвестный/700-мс Telegram не становится победителем.
- Никакого прямого fallback для защищаемого трафика, автоматического отключения масок, снятия проверки сертификатов или TLS downgrade.
- RU-исключения, ручное подтверждение очистки собственного кэша и измеряемый ускоритель сохранены.
- Новых масок MASQUE/Gecko/AWG не объявляется: отдельный серверный контракт не заменён красивым названием. QUIC Initial/SNI не являются невидимыми для всех DPI.

## Материалы и статус изучения
Подобраны восемь конкретных YouTube-материалов, а не выдано обещание «изучить всю сеть». Для OONI доступны фрагменты расшифровки, для части остальных — описание/главы. Недоступный контент не считается просмотренным видео. Основной алгоритмический источник — RFC8305.

| Материал | Что доступно / полезный вывод |
|---|---|
| https://www.youtube.com/watch?v=ZVqExd59GB0 — RIPE/OONI | Фрагменты расшифровки: наблюдаемая сетевая аномалия не обязательно намеренная блокировка; встречается блок всего QUIC или IPv6. Поэтому unknown не превращаем в уверенный диагноз DPI. |
| https://www.youtube.com/watch?v=J8HsLiQjyBY — Dan Kaminsky, DEF CON 19 | Описание и главы: IPv4/IPv6 fragmentation, sequence numbers, TTL. Исторический доклад 2011 года не доказывает работу трюков против DPI 2026 года; пакеты с ошибочными checksum/TTL не включались вслепую. |
| https://www.youtube.com/watch?v=1S3CB1hihks — Packet Pushers, Dual-Stack | Описание: совместная работа IPv4/IPv6 и CLAT; нельзя считать первый IP единственным доступным или просто отключить IPv6 навсегда. |
| https://www.youtube.com/watch?v=0QCQVX9rZ6s — NANOG, Testing IPv6-only Networks | Описание/главы: отдельные тестовые сети dual-stack, IPv6-only, DNS64/NAT64, 464XLAT. Полноценный такой стенд не заявляется. |
| https://www.youtube.com/watch?v=t5OJephyw8I — TCP resets | Поисковые сведения, не полный просмотр. RST требует анализа контекста, не автоматически признак DPI. |
| https://www.youtube.com/watch?v=HTQLipAG27I — TCP retransmissions | Доступны описание и главы о retransmission timeout и реальном примере низкого MTU; полной расшифровки нет. Автоматические MTU/TTL-твики по одному ролику не добавлялись. |
| https://www.youtube.com/watch?v=ZmSQDUBtBFk — IPv6 risks | Поисковые сведения, страница недоступна. Не заявляется аудированная защита от всех IPv6 leaks. |
| https://www.youtube.com/watch?v=4BLmPXXhRBM — QUIC is not Quick Enough | Поисковые сведения о CPU overhead; полный просмотр не заявляется. QUIC не объявлен автоматически быстрее любого TCP. |

Проверенные первичные текстовые источники:
- https://datatracker.ietf.org/doc/html/rfc8305 — чередование адресов, stagger вместо неограниченного simultaneous burst, отмена проигравших; текущая реализация только inspired subset.
- https://www.usenix.org/conference/usenixsecurity25/presentation/zohaib — измеренная SNI-фильтрация QUIC Initial и различия списков фильтрации. Нельзя переносить результат GFW на конкретного российского оператора без измерений. Приёмы перегрузки чужого фильтра в приложение не переносились.

## Проверки и ограничения
34 новых теста на JVM debug/release и Android: глубокий каталог, сохранение порядка и recovery, IPv4/IPv6 interleave, общий deadline, отмена, максимум два dial-сокета, DNS-ошибки/таймауты/ограничение четырёх работников, loopback-альтернатива. Повторяются предыдущие регрессии, всего 218 Android-тестов и 16 снимков существующего UI. Публикация разрешена только после успешного CI, совпадения production-исходников и визуальной проверки этих снимков.

Нет проверки физического телефона, полного пользовательского TUN, аккаунта Telegram, операторского DPI или измеренного прироста скорости/экономии батареи. Рабочие публичные серверы не создаются алгоритмом: при недоступных источниках или строгом пороге поиск может продолжаться долго.
