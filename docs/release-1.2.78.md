# 1.2.78 Experimental — параллельная проверка первого подключения

- Два встроенных Telegram DC проверяются параллельно через тот же локальный SOCKS. Раньше зависание первого DC могло добавить 1,5 секунды к замеру второго и ошибочно отбросить быстрый ответ по порогу 500 мс. Теперь принимается первый валидный MTProto-ответ, а проигравший сокет закрывается.
- Telegram начинается одновременно с HTTPS, а не после него. Оба подтверждения обязательны; отсутствие результата не превращается в успешный маршрут.
- Бюджет обычной пробы первой foreground-попытки Авто сокращён с 6,5 до 1,8 секунды. Это бюджет отдельной пробы, а не гарантия подключения всего приложения за 1,8 секунды. Остальные режимы не получают этот короткий бюджет.
- Между онлайн-волнами теперь 200 мс вместо последовательных секундных пауз. Ожидание отсутствующей сети остаётся 2 секунды; предел четырёх волн и общий кооперативный бюджет 45 секунд сохранены.
- Отмена и завершение пробы освобождают все зарегистрированные HTTP/сокетные ресурсы, а не только последний. Для DC-гонки используются ограниченные общие workers/очередь, не поток на каждый сервер каталога.
- Сохранены HTTPS-сертификаты, проверка nonce и структуры MTProto и строгие ≤500 мс отдельно для HTTPS и Telegram. Прямой обход SOCKS, отключение сертификатов и подключение непроверенного маршрута не добавлены.

## Проверки и ограничения
18 новых JVM-сценариев в debug и release: быстрый второй DC при зависшем первом, неверный nonce, timeout/отмена, параллельный старт HTTP и Telegram, закрытие всех трёх сокетов, гонки регистрации cleanup и бюджеты. HTTP здесь — исключительно управляемый loopback fixture, не замена HTTPS в продукте.

Android выполняет 16 новых сценариев DC/отмены/бюджетов плюс прежние 8 native TLS/Hello/очередь и 1 тест восьми UI-состояний: всего 25. Два HTTP-fixture-сценария остаются JVM-only; политика cleartext Android не ослаблена. UI-снимки визуально просматриваются перед публикацией; release сверяется с фактически проверенными production-исходниками.

Наличие доступного сервера в конкретной сети не гарантируется. Стенд не проверяет физический телефон, полный TUN, Telegram-аккаунт или операторский DPI. Холодные HTTPS/MTProto ≤500 мс — не ICMP ping: медленные, даже пригодные маршруты по-прежнему намеренно отбрасываются. При нуле результатов нужен свежий локальный диагностический отчёт с телефона.
